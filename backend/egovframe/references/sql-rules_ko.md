# SQL 작성 규칙

`egovframe-runtime/persistence-layer/sql-rule.md`에 실린 eGovFrame SQL 작성 규칙을 다룹니다. 아래 번호는 가이드의 번호를 그대로 사용합니다. "SQL 규칙 N"은 규칙 정리 표의 번호이고, "성능 원칙 N"은 "성능을 고려한 SQL 작성 원칙" 표의 번호입니다.

## 적용 범위

- 가이드는 SQL 문법을 통일하여 가독성을 높이는 것을 목적으로 밝히고 있습니다. 즉 이 규칙은 작성 표준이며, 법적 의무나 검수 기준이 아닙니다. 프로젝트에 별도의 SQL 표준이 있다면 그 표준이 우선합니다.
- 이 규칙은 Oracle을 전제로 합니다. FAQ는 `ORA-` 오류만 다루고, "Precompiler", "Static Embedded SQL", "센터컷" 같은 용어는 Oracle 중심의 기존 표준에서 온 것입니다. 그래서 일부 규칙은 다른 DBMS에 적용할 수 없습니다.
- 성능 원칙 2는 iBatis의 `<isNotEmpty>`를 예로 듭니다. MyBatis의 `<if test>`를 비롯한 다른 동적 SQL 태그에도 같은 원칙을 적용합니다.

## 먼저 DBMS를 확인합니다

| 근거 | 확인할 위치 |
|------|-------------|
| JDBC URL 접두어: `jdbc:oracle:`, `jdbc:tibero:`, `jdbc:postgresql:`, `jdbc:mysql:`, `jdbc:mariadb:`, `jdbc:Altibase:`, `jdbc:hsqldb:` | `globals.properties`, `application.yml`·`.properties`, `context-datasource.xml` |
| `Globals.DbType` (값은 프로젝트마다 다릅니다. 예: `mysql`, `mariadb`, `oracle`, `postgresql`, `hsql`) | 공통컴포넌트 기반 프로젝트의 `globals.properties`나 `application.properties` |
| JDBC 드라이버 의존성 | `pom.xml`, `build.gradle` |
| 매퍼 위치에 들어 있는 SQL 파일 접미어 (예: `*_${Globals.DbType}.xml`) | SQL 세션 설정 (`context-mapper.xml` 또는 Java 설정) |

- 모듈마다 DBMS별 SQL 파일이 따로 있다면, 현재 DBMS에 대해 매퍼 위치 설정이 실제로 로드하는 파일만 검토합니다.
- 현재 DBMS에 해당하는 파일이 없다면 그 사실을 `R` 사항으로 보고합니다(`architecture_ko.md`의 "저장 방식" 절, 1번 규칙). 그다음 가장 가까운 DBMS의 파일(MariaDB라면 MySQL)을 검토하고, 그렇게 판단했다는 점을 보고서에 밝힙니다.
- 이 규칙들에 관해서는 MariaDB와 MySQL이 같은 SQL을 받아들입니다. 다만 `Globals.DbType`이 `mariadb`인데 `*_mysql.xml` 파일만 있다면, 파일 내용은 문제가 없지만 매퍼 위치 설정이 아무 파일도 로드하지 못합니다(`architecture_ko.md`의 "저장 방식" 절, 1번 규칙).
- HSQLDB, MySQL, MariaDB, PostgreSQL은 Oracle 계열이 아니므로 B 묶음을 적용하지 않습니다. 그 밖의 DBMS(예: Altibase, CUBRID)는 B 묶음을 적용하기 전에 Oracle의 `(+)` 조인과 힌트 문법을 지원하는지 확인합니다(이 스킬에서는 미검증).

그다음 아래 묶음을 순서대로 적용합니다.

| 묶음 | 적용 대상 | 보고 방식 |
|------|-----------|-----------|
| A. 공통 규칙 | 모든 DBMS | 위반 (`R`) |
| B. Oracle 계열 규칙 | Oracle과 Tibero만 해당합니다(Tibero 호환성은 미검증이므로 프로젝트에서 확인합니다) | Oracle 계열에서는 위반 (`R`), 그 밖의 DBMS에서는 해당 없음 |
| C. 바꿔서 적용하는 규칙 | 모든 DBMS에 적용하되, 해당 DBMS의 대응 함수를 사용합니다 | 원칙에 대한 위반 (`R`) |
| D. 정책 규칙 | 모든 DBMS | 프로젝트에 확인할 사항 (`G`)이며, 위반으로 보고하지 않습니다 |

## A. 공통 규칙

| 번호 | 규칙 | 검사 방법 |
|------|------|-----------|
| SQL 규칙 1 | 한 줄은 80칼럼 이하로 작성하기를 권장하며, 120칼럼을 넘지 않아야 합니다 | SQL 본문에서 120자를 넘는 줄을 찾습니다 |
| SQL 규칙 2 | SQL 키워드는 대문자로 작성합니다 | 소문자로 쓴 `select`, `from`, `where` 등을 찾습니다 |
| SQL 규칙 3 | 들여쓰기에는 공백을 사용하고, 탭은 사용하지 않습니다 | 매퍼 XML의 SQL 안에서 탭 문자를 찾습니다 |
| SQL 규칙 4, 성능 원칙 6 | 애플리케이션에서 사용하는 칼럼만 나열합니다. `SELECT *`는 허용하지 않습니다 | `SELECT *`와 `A.*`를 찾습니다 |
| SQL 규칙 5 | 줄은 키워드, 테이블, 칼럼 단위로 바꿉니다 | SELECT, INSERT, UPDATE 목록에서 한 줄에 칼럼이 하나씩 있는지 확인합니다 |
| SQL 규칙 6 | 콤마 뒤에는 공백을 한 칸 둡니다 | 공백 없이 `,X`로 붙은 곳을 찾습니다 |
| SQL 규칙 7 | 여는 괄호 바로 뒤에는 공백을 두지 않습니다 | `( X` 형태를 찾습니다 |
| SQL 규칙 8 | 주석은 `/* */`를 사용하고, `--`는 사용하지 않습니다 | SQL 안에서 `--`를 찾습니다 |
| SQL 규칙 10, 성능 원칙 10 | WHERE 절의 비교 값은 모두 바인드 변수로 처리하며, 리터럴 SQL은 금지합니다. MyBatis에서는 `#{}`를 사용합니다. `${}`는 리터럴 SQL을 만들 뿐 아니라 SQL 인젝션 위험도 있습니다 | `${`(SQL 인젝션 위험이 있으므로 가장 먼저 보고합니다)와 WHERE 절의 따옴표 리터럴을 찾습니다. `USE_AT = 'Y'` 같은 고정 상태 코드는 공식 공통컴포넌트에도 있으므로, 줄마다 보고하지 말고 낮은 우선순위로 한 번만 보고합니다 |
| SQL 규칙 12, 성능 원칙 3 | 인라인 뷰는 최대 3단계까지만 중첩합니다(2단계 권장) | `FROM (SELECT`가 몇 단계로 중첩되는지 셉니다 |
| SQL 규칙 13 | `DECODE`나 `CASE WHEN`에서 데이터 값을 하드코딩하여 비교하지 않습니다 | `CASE WHEN X = '01'`처럼 리터럴 코드와 비교하는 곳을 찾습니다 |
| 작성 예시 | 콤마는 앞쪽에 둡니다. 한 줄에 칼럼 하나를 적습니다. 테이블 별칭은 FROM에 나온 순서대로 `A`, `B`, `C`를 씁니다. 모든 칼럼 별칭 앞에 `AS`를 붙이고, 스칼라 서브쿼리 결과에는 항상 별칭을 붙입니다 | SELECT 작성 형식을 이 항목들과 비교합니다 |
| 작성 예시 | `SELECT`, `FROM`, `WHERE`, `AND`는 SELECT의 "T"를 기준으로 오른쪽 정렬합니다. INSERT의 절은 INSERT의 "T", UPDATE와 DELETE의 절은 마지막 글자 "E"를 기준으로 정렬합니다 | 키워드 정렬을 확인합니다 |
| 작성 예시 | WHERE 절에는 조인 조건을 먼저 적고, 그 뒤에 필터 조건을 적습니다 | 조건의 순서를 확인합니다 |
| DELETE 예시 | DELETE의 WHERE 절은 생략하지 않습니다 | `WHERE`가 없는 `DELETE FROM`을 찾습니다 |
| 성능 원칙 5 | SELECT나 WHERE 절에서 칼럼을 불필요하게 가공하지 않습니다(인덱스를 사용하지 못하게 됩니다) | WHERE 절에서 인덱스 칼럼에 함수를 적용한 곳을 찾습니다 |
| 성능 원칙 9 | 최댓값을 가진 행을 찾거나 정렬된 데이터를 추출할 때는 인덱스를 활용하여 정렬 작업을 최소화합니다 | `ORDER BY`와 `ROWNUM`·`LIMIT`을 함께 쓰는 쿼리를 검토합니다 |
| 성능 원칙 11 | HAVING보다 WHERE 절에서 필터링합니다 | 집계 함수를 쓰지 않는 HAVING 조건을 찾습니다 |
| 성능 원칙 13 | OR 연산자 사용을 최소화합니다 | 길게 이어진 OR 조건을 검토합니다 |
| 성능 원칙 14 | 조회 데이터에 UNIQUE 제약 조건이 없다면 `UNION ALL`을 사용하고, `UNION`은 사용하지 않습니다 | 뒤에 `ALL`이 없는 `UNION`을 찾습니다 |
| 성능 원칙 15 | 애플리케이션의 반복문 안에서 INSERT, UPDATE, DELETE를 반복해서 호출하지 않고, 컬렉션으로 한 번에 처리합니다 | Java의 `for`·`while` 반복문 안에서 Mapper·DAO의 쓰기 메서드를 호출하는 곳을 찾습니다 |
| 성능 원칙 16 | FROM 절에는 테이블을 4개 이하로 사용합니다(조인 조건 3개) | FROM 절마다 테이블 수를 셉니다 |

## B. Oracle 계열 규칙

| 번호 | 규칙 | Oracle 전용인 이유 |
|------|------|--------------------|
| SQL 규칙 11 | ANSI SQL-92 방식의 조인(`JOIN ... ON`)은 사용하지 않습니다. 다만 업무상 `FULL OUTER JOIN`이 필요한 경우는 허용합니다 | 이 규칙은 Oracle의 `(+)` 외부 조인 문법을 전제로 합니다. PostgreSQL과 MySQL에는 `(+)` 문법이 없어서 외부 조인을 ANSI 방식으로만 작성할 수 있으므로, 이 규칙을 지킬 수 없습니다 |
| SQL 규칙 9 | 힌트는 `/*+ */`만 사용하고(`--+`는 사용하지 않음), `INDEX`와 `INDEX_DESC`만 허용합니다. 그 밖의 힌트는 튜닝 담당자와 협의해야 합니다 | PostgreSQL에는 기본 힌트 기능이 없습니다. MySQL은 같은 주석 표기를 쓰지만 힌트 이름이 다릅니다 |
| FAQ | `ORA-01555`, `ORA-01003`, `ORA-00600`, `ORA-00060` 오류 대응 | Oracle 오류 코드입니다 |

Oracle 계열이 아닌 DBMS에서는 SQL 규칙 9와 11을 위반으로 보고하지 말고, 해당하지 않는 규칙이라고 밝힙니다.

## C. 바꿔서 적용하는 규칙

| 번호 | 규칙 | 다른 DBMS에서 적용하는 방법 |
|------|------|------------------------------|
| 성능 원칙 7 | 여러 조건을 비교할 때는 `DECODE`보다 `CASE WHEN`을 사용합니다 | `DECODE`는 Oracle 전용 함수입니다. 다른 DBMS에서는 원래 `CASE`만 쓸 수 있으므로 자동으로 충족됩니다 |
| 성능 원칙 8 | `NVL`을 과도하게 사용하지 않습니다 | `COALESCE`, `IFNULL`, `ISNULL`에도 같은 제한을 적용합니다 |
| SQL 규칙 14, 성능 원칙 12 | 정적(Static Embedded) SQL을 원칙으로 합니다. `MERGE INTO`는 허용합니다. `WITH` 절은 배치에서만 허용하고, 온라인 환경에서는 사용하지 않습니다 | `WITH` 제한은 모든 DBMS에 그대로 적용하되, 가이드가 근거로 든 "임시 테이블 생성"은 Oracle의 동작이라는 점을 함께 밝힙니다. MySQL에는 `MERGE INTO`가 없습니다 |

## D. 정책 규칙

아래 규칙은 기술적인 근거 없이 제한을 두거나, 화면 종류에 따라 달라집니다. 프로젝트에 확인할 사항으로 보고합니다.

| 번호 | 규칙 |
|------|------|
| 성능 원칙 1 | 조회나 변경에서 뷰를 통한 접근은 허용하지 않습니다 |
| 성능 원칙 2 | WHERE 조건은 항상 정적으로 사용하기를 권장합니다. `<isNotEmpty>`(MyBatis의 `<if test>`) 같은 동적 태그를 남용하지 않습니다 |
| 성능 원칙 4 | 스칼라 서브쿼리 안에서 데이터를 가공하지 않습니다. 배치 프로그램에서는 스칼라 서브쿼리를 사용하지 않습니다 |
| 성능 원칙 17 | 분석 함수는 통계 화면에서만 사용합니다 |
| 성능 원칙 18 | 스칼라 서브쿼리는 10,000건 이하의 테이블에서만 사용합니다 |

## 자동 검사

이 스킬 폴더의 `scripts/check_sql.py`는 A 묶음 규칙 가운데 패턴 검색으로 정확하게 찾을 수 있는 규칙을 매퍼 XML 파일에서 검사합니다. 파일을 읽기만 하고, Python 3만 있으면 실행되며, `target`이나 `build` 같은 빌드 산출물 폴더는 건너뜁니다.

```bash
python <스킬 폴더>/scripts/check_sql.py src/main/resources --dbms mysql
```

| 찾아내는 항목 | 규칙 |
|---------------|------|
| `${}` | SQL 규칙 10 |
| SQL 안의 탭 문자 | SQL 규칙 3 |
| SQL 안의 `--` 주석 | SQL 규칙 8 |
| `SELECT *`, `A.*` | SQL 규칙 4 |
| 120칼럼을 넘는 SQL 줄 | SQL 규칙 1 |
| 소문자 키워드 (구문마다 첫 번째만) | SQL 규칙 2 |
| `ALL`이 없는 `UNION` | 성능 원칙 14 |
| WHERE가 없는 DELETE | DELETE 예시 |

- 먼저 매퍼 위치 설정이 해당 파일을 로드하는지 확인합니다(`architecture_ko.md`의 "저장 방식" 절, 1번 규칙). 로드되지 않는 파일의 검사 결과는 의미가 없으므로, 그 대신 로딩 문제를 보고합니다.
- DBMS마다 SQL 파일을 따로 두는 프로젝트에서는 `--dbms`에 현재 `Globals.DbType` 값을 넣어서 실행합니다.
- 결과는 `경로:행: [규칙] 메시지` 형식으로 출력되며, 발견한 사항이 있으면 종료 코드가 1입니다.
- 이 스크립트는 작성 형식, 정렬, 조인 순서, 따옴표 리터럴, B·C·D 묶음 규칙은 검사하지 않습니다. 이런 규칙은 SQL을 직접 읽으면서 검토합니다.
- 한 규칙의 위반이 매우 많다면(예: 모든 파일에 탭이 있는 경우), 줄마다 나열하지 말고 규칙별 개수로 요약해서 보고합니다.

## 예시

작성 형식 규칙에 맞춘 SELECT입니다(Oracle 계열).

```sql
SELECT A.ID          AS ID        /* ID */
     , A.NAME        AS NAME      /* 이름 */
     , B.DEPT_NAME   AS DEPT_NAME /* 부서명 */
  FROM SAMPLE A                   /* 샘플 */
     , DEPT B                     /* 부서 */
 WHERE A.DEPT_ID = B.DEPT_ID
   AND A.USE_YN = #{useYn}
 ORDER BY A.ID
```

PostgreSQL이나 MySQL에서 외부 조인이 필요하면 같은 쿼리를 `JOIN ... ON`으로 작성하고, 나머지 규칙은 모두 그대로 지킵니다.
