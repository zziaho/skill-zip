# 설계단계 보안설계 기준

고시 별표3에 정의되어 있고 개발보안 가이드 제3장과 진단가이드 PART3에서 설명하는 설계단계 기준 20개입니다. 구현을 시작하기 전에 분석·설계 산출물을 대상으로 점검합니다.

강도 표기: 이 파일에서 각 기준 아래의 번호가 붙은 요구사항은 `R`입니다. **점검 사항**과 **테스트 계획** 항목은 `G`이며, 설계의 증거로 가이드가 제시하는 내용입니다. `D`로 표시한 항목은 이 스킬의 판단입니다.

## 설계 진단의 진행 방식

- **시기**: 설계가 끝나고 구현을 시작했거나 시작을 준비하고 있을 때입니다.
- **검토 대상**: 요구사항정의서, 아키텍처설계서, 프로그램·클래스·컴포넌트·유스케이스 명세서, DB설계서, 초기 데이터 설계서, 요구사항추적표, 단위 테스트 케이스, 프로젝트의 개발가이드(표준코딩정의서) 같은 분석·설계 산출물입니다.
- **요구사항마다 두 가지 질문**: 아래의 번호가 붙은 요구사항마다 진단가이드는 (1) 산출물에 해당 요구사항의 보안 설계가 있는지, (2) 이를 확인할 테스트 계획이 있는지를 묻습니다. 테스트 계획이 없는 경우도 미비점으로 보고합니다(`D`: 가이드는 두 질문을 모두 하지만, 테스트 계획이 없을 때 어떻게 평가하는지는 설명하지 않습니다).
- **식별을 먼저**: 분석 단계에서 프로젝트는 중요정보와 중요 기능을 분류합니다. 기준 SR2-1, SR2-4, SR2-7, SR2-8은 이 분류에 의존하므로 분류 결과를 먼저 요청합니다.
- **근거**: 결함마다 객관적인 근거(이 가이드나 법령), 실무적인 개선 방안, 부족한 부분을 보여 주는 산출물이 필요합니다.
- **명칭**: 제3장은 기준에 1.1부터 4.1까지 번호를 붙이고, 부록과 산출물 예시는 SR1-1부터 SR4-1까지를 사용합니다. 둘은 같은 번호입니다(1.n = SR1-n). 보고서에는 SR 형식을 사용합니다.

설계항목 적용계획서는 기준마다 유형, 요구사항 번호, 기준 이름, 대응 방안, 적용 방법, 비고("코딩 표준에 정의함"이 많습니다)를 나열합니다. 가능하면 프레임워크나 공통 라이브러리로 기준을 적용하고, 그 라이브러리 자체의 보안도 검토합니다.

## SR1: 입력데이터 검증 및 표현

### SR1-1 DBMS 조회 및 결과 검증

1. 애플리케이션이 최소 권한 계정으로 DB에 접속합니다.
2. 외부 입력으로 SQL을 동적으로 만들지 않습니다.
3. 동적 SQL을 피할 수 없다면 입력을 먼저 검증합니다.

- **점검 사항**: 애플리케이션마다 필요한 읽기, 쓰기, 수정, 삭제 권한만 가진 DB 계정을 하나씩 사용하는지(초기 데이터 설계서, 기존 개발 서버라면 실제 부여된 권한), 아키텍처설계서에 ORM이나 정적 쿼리 환경이 있는지, 개발가이드에 코딩 규칙(MyBatis/iBatis의 `#{}`, `PreparedStatement`)이 있는지, 동적 쿼리라면 모든 DB 접근에 적용하는 필터가 있는지(호출마다 적용한다면 코딩 규칙)를 확인합니다
- **테스트 계획**: 특수문자(`' " = & | ! ( ) { } $ % @`), 키워드(`UNION`, `SELECT`, `IF`, `END`), 함수(`DATABASE()`, `CONCAT()`, `COUNT()`), 계정의 권한을 벗어나는 요청

### SR1-2 XML 조회 및 결과 검증

1. XML 쿼리(XPath, XQuery)의 파라미터를 필터링하거나, 타입별로 prepared 쿼리에 바인딩합니다.

- **점검 사항**: 프로그램, 컴포넌트, 클래스 설계에 필터나 안전한 라이브러리가 있는지, 코딩 규칙이 있는지 확인합니다. 가이드는 `" [ ] / = @`를 필터링할 문자로 제시합니다
- **보완할 점**: 제3장에는 XXE(보안약점 8)에 대한 설계 대응 방안이 사고 사례 외에는 없습니다. XML 파서가 DTD와 외부 개체를 비활성화한다는 규칙을 추가합니다(`D`)

### SR1-3 디렉토리 서비스 조회 및 결과 검증

1. 인증에 LDAP을 사용할 때는 요청에 사용하는 입력을 LDAP 삽입에 대비해 필터링합니다.

- **점검 사항**: 검색 필터 입력(`= + < > # ; \`)에 대한 필터나 안전한 라이브러리가 있는지, 코딩 규칙이 있는지 확인합니다

### SR1-4 시스템 자원 접근 및 명령어 수행 입력값 검증

1. 입력이 시스템 자원(IP, 포트, 프로세스, 메모리, 파일)을 지정할 때, 허가되지 않은 자원을 사용할 수 없습니다.
2. 서버가 셸 명령어를 실행해야 할 때, 입력으로 악의적인 명령어를 실행할 수 없습니다.

- **점검 사항**: 기능별로 허용하는 자원을 목록으로 관리하는지(프로퍼티나 XML에 두어서 변경할 때 코드를 거의 바꾸지 않게 함), 목록으로 관리할 수 없다면 `..`, `/`, `\`를 제거하고 고정된 경로로 접근을 제한하는 규칙이 있는지, 자원 접근을 로그로 남기는지(시각, 사용자 ID, IP, 입력, 거부된 접근 포함) 확인합니다. 셸 실행은 피합니다. 필요하다면 명령어와 인자를 허용 목록에서 가져오고 입력은 그 목록의 인덱스로만 사용하며, 실행한 명령어를 로그로 남깁니다
- **테스트 계획**: 경로 문자 `.. / \`, 명령어 구분자 `| & ;`

### SR1-5 웹 서비스 요청 및 결과 검증

1. 동적 응답 페이지에 사용하는 입력이 XSS 필터를 거칩니다.
2. 동적 응답 페이지에 사용하는 DB 결과를 HTML 인코딩하거나 XSS 필터링합니다.

- **점검 사항**: 입력에 대한 필터, 인터셉터, 공통 검증기가 있는지, 출력에 대한 뷰 계층의 HTML 인코딩이 있는지(DB 값 포함), 허용 목록 기반의 필터 규칙이 있는지, 서블릿 필터를 사용한다면 URL 매핑이 모든 대상을 포함하는지 확인합니다. 가이드가 제시하는 라이브러리는 LUCY XSS Filter, OWASP ESAPI(Java)입니다
- **테스트 계획**: `<IMG SRC="javascript:alert('XSS');">` 같은 필터 우회 입력

### SR1-6 웹 기반 중요 기능 수행 요청 유효성 검증

1. 모든 요청이 실제 사용자가 보낸 유효한 요청인지 판단할 수 있습니다.

- **점검 사항**: 데이터를 변경하는 모든 요청에 CSRF 토큰(세션별로 발급하고, hidden 필드로 전송하며, 처리할 때 비교함. Spring이나 Struts에서는 인터셉터가 자동으로 검사함)이나 CAPTCHA가 있는지, 중요 기능에 재인증이 있는지 확인합니다. Spring Security는 3.2부터 CSRF 보호를 제공합니다
- **테스트 계획**: 자동화된 스크립트 요청이 차단됩니다

### SR1-7 HTTP 프로토콜 유효성 검증

1. 쿠키나 헤더에 사용하는 입력을 응답 분할에 대비해 필터링합니다.
2. 리다이렉트나 포워드 URL로 사용하는 입력은 허용 목록에서 선택하는 데에만 사용합니다.

- **점검 사항**: 헤더를 설정하는 함수(`setHeader`, `addCookie`, `sendRedirect`)를 식별해서 CR/LF를 제거하는지, 허용하는 도메인과 주소를 정의하고(코드나 XML/프로퍼티) 검증 모듈이 있는지 확인합니다
- **테스트 계획**: CR/LF가 들어 있는 값, 임의의 URL

### SR1-8 허용된 범위내 메모리 접근

1. 프로그램이 메모리를 직접 관리하는 경우(C, C++), 버퍼 경계를 넘는 읽기와 쓰기를 막습니다.
2. 버퍼 오버플로우를 일으킬 수 있는 취약한 API를 금지합니다.

- **점검 사항**: 플랫폼의 실행 불가능 스택, ASLR, StackGuard, 배열을 복사할 때 길이를 검사하는 규칙, 개발가이드의 금지 함수 목록과 대체 함수(보안약점 49 참조)를 확인합니다
- **테스트 계획**: 충분히 긴 문자열

### SR1-9 보안기능 입력값 검증

1. 역할과 권한을 결정하는 정보를 서버에서 관리합니다(제3장은 클라이언트가 보낸 신원 정보를 사용하기 전에 검증한다는 내용을 추가합니다).
2. 보안 기능의 인자로 사용하는 외부 입력(쿠키, 환경 변수, 파라미터)을 검증하고 제한적으로 사용합니다.
3. 중요한 상태나 인증·인가 데이터를 쿠키로 전송하지 않습니다. 불가피하다면 암호화합니다.

- **점검 사항**: 역할(사용자, 관리자, 슈퍼 관리자)과 그 권한을 정의해서 DB나 세션에 저장하는지, 권한 검사가 서버의 데이터를 사용하는지, 보안 기능에 사용하는 입력마다 종류, 출처, 사용 이유, 검증 방법(null 검사, 정수 오버플로우를 막는 범위 검사)이 있는지, 쿠키 목록(이름, 값, 의미, 수명)과 중요한 쿠키를 사용하는 이유가 있는지, 암호화, 무결성 검사(HMAC), 보안 채널 전용 속성이 있는지 확인합니다. 외부 인증 서비스를 사용한다면 백채널로 결과를 검증합니다
- **테스트 계획**: 변조한 파라미터와 쿠키로 권한 검사를 우회하려고 시도합니다

### SR1-10 업로드·다운로드 파일 검증

1. 업로드 파일의 유형, 크기, 개수, 실행 권한을 제한합니다.
2. 저장된 업로드 파일을 외부에서 식별할 수 없습니다.
3. 요청한 다운로드 파일 이름을 검증합니다.
4. 다운로드한 소스 코드나 실행 파일의 무결성을 검사합니다.

- **점검 사항**: 프레임워크에 크기 제한이 있는지(가이드의 예시: Spring `CommonsMultipartResolver`의 `maxUploadSize` 20 MB, `maxInMemorySize` 1 MB), 모든 업로드에 적용하는 공통 모듈이 MIME 타입과 확장자를 검사하는지(클라이언트와 서버에 같은 정책을 적용함), 업로드 경로에서 파일을 실행할 수 없는지, URL로 접근할 수 없는 디렉터리에 저장하고 컨트롤러를 거쳐 다운로드하는지, 무작위 저장 이름을 DB 테이블에서 원래 이름과 대응시키는지, 다운로드 파일 이름에서 `.. / \`를 제거하고 DB와 사용자 권한으로 확인하며 악성코드를 검사하는지, 다운로드한 코드에 대한 체크섬이나 해시를 제공하고 검증하는지 확인합니다
- **테스트 계획**: 허용하지 않는 유형, 크기, 개수, 저장된 파일의 실행, 이름에 들어간 `../`와 `..\`, 파라미터를 바꿔서 다른 파일 요청, 변조한 파일

## SR2: 보안기능

### SR2-1 인증 대상 및 방식

1. 중요 기능과 자원은 인증한 뒤에만 사용합니다.
2. 안전한 인증 방식으로 우회와 권한 상승을 막습니다.
3. 중요 기능에는 2단계 인증을 고려합니다.

- **점검 사항**: 요구사항에서 중요 기능과 자원을 분류했는지, 누락이 없도록 인증을 중앙에서 적용하는지(프레임워크 컴포넌트나 기능과 인증의 매핑), 인증 데이터를 서버에 저장하고 서버에서 검사하며 암호화하는지, 시도 횟수 제한과 오류 처리가 있는지, 인증 실패를 로그로 남기는지(시각, IP, ID), 개인정보 변경, 패스워드 재설정, 권한 관리, 관리자 기능에 추가 인증이 있고 그 사용과 실패를 로그로 남기는지 확인합니다
- **OTP**: 시간, 이벤트, 챌린지 기반입니다. 유효 시간이 있습니다(금융권은 30초에서 60초). 6자리 이상의 숫자나 문자입니다
- **2단계 인증**: 지식(패스워드, PIN), 소유(토큰, 스마트카드), 고유 특성(지문, 홍채) 중 두 가지를 사용합니다. 또는 다중 기기(SMS, ARS), 인증서, 생체 서명을 사용합니다
- **테스트 계획**: 인증 없이 중요 기능에 접근합니다

### SR2-2 인증 수행 제한

1. 로그인 시도를 제한하고, 제한을 넘으면 제한 조치를 적용합니다.
2. 추적할 수 있도록 실패한 시도를 로그로 남깁니다.

- **점검 사항**: 제한 횟수(제3장과 진단가이드는 3회에서 5회라고 설명하고, 두 가이드의 산출물 예시는 5회이며, 진단가이드의 예시는 5회 실패를 넘으면 24시간 잠금을 추가함), 사용자 ID와 세션별로 실패 횟수를 영속적으로(DB나 파일) 저장하는지, 제한을 넘으면 계정 잠금이나 추가 정보를 요구하는지, CAPTCHA가 있는지, 사용자 테이블에 실패 횟수, 잠금 상태, 마지막 성공 시각과 실패 시각, 로그아웃 시각이 있는지, 로그에 사용자 ID, 실패 횟수, 시각, IP, 계정 상태가 있는지 확인합니다
- **테스트 계획**: 반복된 실패가 제한 조치를 일으키고 영속적으로 기록됩니다

### SR2-3 비밀번호 관리

1. 패스워드 규칙은 KISA 『패스워드 선택 및 이용 안내서』를 따릅니다(부록은 『암호이용안내서』를 인용합니다).
2. 네트워크로 전송하는 패스워드는 암호화하거나 암호화된 채널로 전송합니다.
3. 패스워드는 솔트를 적용한 안전한 해시로 저장하며, 해시는 서버에서 계산합니다.
4. 패스워드 변경과 재설정은 안전한 규칙을 따릅니다.
5. 패스워드 관리 규칙을 정의하고 적용합니다.

- **규칙**: 두 가지 이상의 문자 종류를 조합해서 8자 이상이거나 10자 이상이어야 합니다. 반복 패턴이나 키보드 배열 패턴, 개인정보, 사용자 ID, 사전 단어, 유명 인물 이름, 유사 문자 치환, 기본 패스워드를 사용하지 않습니다
- **전송**: 공용 네트워크에서는 TLS나 VPN을 사용하고, 최신 TLS 버전(예: TLS 1.2와 1.3)만 사용하며 KISA 『암호 알고리즘 및 키 길이 이용 안내서』의 알고리즘 조합을 사용합니다
- **저장**: 패스워드마다 고유한 솔트를 32바이트 이상으로 적용한 일방향 해시입니다. 진단가이드는 SHA-224/256/384/512를 제시합니다. 제3장은 솔트를 다이제스트와 함께 DB에 저장하고, 진단가이드는 암호화 키를 저장하는 곳에 저장하라고 설명합니다. `D`: 둘 중 어느 쪽도 허용하는 것으로 보고 프로젝트의 키 관리 설계를 따릅니다
- **변경과 재설정**: 변경할 때 현재 패스워드를 확인합니다. 본인 확인(휴대전화, i-PIN, 인증서, 카드)을 거친 뒤에만, 그리고 회원 가입할 때 등록한 이메일로만 재설정합니다. 질문과 답변의 실패 횟수를 제한합니다. 임시 패스워드를 발급하고 처음 로그인할 때 변경하도록 강제합니다. 이전 패스워드를 재사용하지 못하게 합니다
- **관리**: 3개월(또는 6개월)마다 변경하고 만료일을 사용자 테이블에서 추적합니다. 마지막 로그인 성공 시각을 저장하고 보여 줍니다
- **테스트 계획**: 규칙의 강제 적용, 패킷 스니핑, 저장된 값에 대한 크래킹 도구, 본인 확인 우회나 재설정 페이지에 직접 접근

### SR2-4 중요자원 접근통제

1. 중요 자원의 접근 통제 정책을 수립합니다.
2. 중요 기능의 접근 통제 정책을 수립합니다.
3. 관리자 페이지의 접근 통제 정책을 수립합니다.

- **점검 사항**: 접근 통제를 세 수준으로 나누는지(진단가이드의 설계 예시), 즉 화면(사용자가 쓸 수 없는 기능의 버튼이나 링크를 표시하지 않음), 기능(URL을 직접 입력해도 서버가 요청마다 권한을 검사함), 데이터(서버가 해당 레코드에 대한 권한을 검사함) 수준을 확인합니다. 필터나 인터셉터로 적용하는 공통 모듈이 있는지, 관리자 기능을 물리적으로나 논리적으로 분리했는지, 중요 자원(파일, 프로세스, 메모리, DB, 정보)과 주체를 식별했는지, 최소 권한과 권한 분리가 적용되었는지, 역할에는 RBAC를, 자원에는 ACL을 적용하는지(Spring Security이며, 메서드를 호출하기 전후에 도메인 객체의 권한을 검사하는 ACL 모듈을 포함함), 프레임워크로 적용한다면 모든 요청을 포함하는지, 중요 기능을 익명, 사용자, 특권, 관리자 영역으로 분리하고 파라미터 변조 검사를 하며 권한을 가능한 한 늦게 상승시키고 바로 낮추는지, 관리자 페이지에 추측하기 어려운 URL과 별도 포트, 외부 네트워크 차단, 지정된 IP로의 제한, 암호화된 채널, 추가 인증, 접근 로그가 있는지 확인합니다
- **테스트 계획**: 부여된 권한을 넘는 작업, 외부에서 관리자 접근, 관리자 트래픽 스니핑

### SR2-5 암호키 관리

1. DB 암호화 키는 KISA 『암호이용안내서』가 정의한 방식으로 관리합니다(제3장은 대신 『암호 키 관리 안내서』(2014)를 인용합니다).
2. 설정 파일(XML, 프로퍼티)의 중요한 값을 암호화하는 키는 그 자체를 암호화해서 별도의 디렉터리에 저장합니다.

- **점검 사항**: DB 키를 DB와 물리적으로 분리해서 저장하는지, 생성, 배포, 사용, 폐기 정책이 명시되어 있는지, 패스워드와 키를 메모리에 보관하지 않거나 사용한 뒤에 0으로 채우는지, 생성할 때와 변경할 때 백업하는지, 조직에 맞는 FIPS 140-2 수준을 선택했는지, 키 복구 절차가 있는지, 키 유형별 유효 기간이 있는지(가이드의 NIST 수치: 송신자의 대칭키는 최대 2년, 공개 암호화 키와 개인 복호화 키는 최대 2년, 서명 키는 1년에서 3년), 설정 파일의 비밀 정보를 다른 곳에 보관한 마스터 키로 암호화하는지 확인합니다
- **테스트 계획**: 설정 파일의 비밀 정보가 암호화되어 있는지, 키를 어디에 보관하는지

### SR2-6 암호연산

1. 대칭 암호화와 비대칭 암호화는 KISA 『암호이용 안내서』의 알고리즘과 키 길이를 사용합니다.
2. 일방향 암호화는 솔트를 적용한 안전한 해시를 사용합니다.
3. 난수는 안전한 생성기에서 얻습니다.

- **점검 사항**: 대칭 알고리즘은 SEED, ARIA, AES, 비대칭 알고리즘은 RSA, KCDSA, ECC이고, 키 길이는 대칭 128비트 이상, 비대칭 2048비트 이상인지(진단가이드) 확인합니다. 제3장의 NIST 표는 2030년까지 112비트 보안 강도, 그 이후에는 128비트(RSA 3072, ECC 256)를 요구하며, 권장 목록에는 SHA-2뿐 아니라 SHA-3과 LSH도 포함됩니다. 해시는 목적(MAC, 키 유도, 난수 생성, 서명)에 따라 선택하고, 난수는 FIPS 140-2 검증 모듈에서 256비트 이상의 시드로 생성합니다
- **`D`**: 진단가이드의 코딩 규칙 예시는 `java.util.Random`을 안전한 API로 제시합니다. `java.security.SecureRandom`만 안전한 것으로 취급합니다(보안약점 25 참조)
- **테스트 계획**: 암호화된 데이터를 복호화하거나 크래킹하려는 시도

### SR2-7 중요정보 저장

1. 중요정보나 개인정보를 암호화해서 저장합니다.
2. 필요하지 않은 중요정보를 메모리에 남기지 않습니다.

- **암호화 대상**(진단가이드의 목록): 개인정보보호법에 따른 고유식별정보(주민등록번호, 운전면허번호, 여권번호, 외국인등록번호), 생체정보, 패스워드, 정보통신망법에 따른 주민등록번호, 신용카드번호, 계좌번호, 위치정보법에 따른 위치정보, DB 계정과 연동 계정, 주요 설정값 같은 시스템 비밀 정보
- **점검 사항**: 중요 데이터가 벗어나지 않는 안전한 영역이 있는지, SR2-6의 알고리즘과 키로 암호화하는지, 쿠키와 HTML5 로컬 스토리지에 중요 데이터가 없는지(불가피하다면 암호화), 중요한 로직과 주석이 서버 측 코드에만 있는지, 개인정보와 금융 정보 기능에서 사용한 뒤에 메모리를 0으로 채우는지, 중요한 페이지에서 캐싱을 비활성화하는지, 인증 정보 입력 폼에 `autocomplete="off"`를 설정하는지 확인합니다
- 산출물 예시는 "중요정보를 노출하는 주석 금지"와 "저장된 파일 이름과 경로 비노출"도 SR2-7로 분류합니다
- **`D`**: `autocomplete="username"`과 `"current-password"`를 설정한 로그인 폼은 미비점으로 보고하지 않습니다. KWCAG 2.2 7.3.3 접근 가능한 인증과 KRDS(`krds` 스킬의 `application-flow.md`)는 비밀번호 관리자와 붙여넣기가 동작해야 한다고 요구하고, 현재 대부분의 브라우저는 로그인 필드에 설정한 `autocomplete="off"`를 무시합니다. 그 대신 프로젝트의 보안 설계 산출물에 이 선택이 기록되어 있는지 확인합니다. 일회용 인증 코드, 카드 번호, 주민등록번호 같은 다른 중요 입력 필드에는 `autocomplete="off"`를 유지합니다

### SR2-8 중요정보 전송

1. 인증 정보 같은 중요정보를 전송할 때 암호화합니다.
2. 쿠키에 담긴 중요정보를 전송할 때 암호화합니다.

- **점검 사항**: 보호할 데이터가 정의되어 있는지(SR2-7과 같은 목록), 종단 사이에 TLS나 VPN을 사용하는지(보안 채널이 없을 때는 안전한 알고리즘으로 암호화하는지), hidden 필드와 Ajax 변수, 쿠키, 헤더에 불필요한 데이터가 없는지, 중요한 쿠키를 사용하지 않거나 세션 쿠키로 만들고 암호화하는지 확인합니다(진단가이드는 "TLSv2"라고 적고 있습니다. `D`: SR2-3처럼 TLS 1.2 이상으로 해석합니다)
- **테스트 계획**: 패킷 스니핑

## SR3: 에러처리

### SR3-1 예외처리

1. 명시적인 예외는 예외 블록에서 처리합니다.
2. 입력 범위를 검사해서 런타임 예외를 예방합니다.
3. 상세한 오류 정보를 사용자에게 보여 주지 않습니다.

- **점검 사항**: 개발가이드의 예외 유형별 처리(시스템 정보를 절대 노출하지 않고, 예외를 반드시 처리하며, 경우별로 처리를 구분함), 예외 로그 정책(시각, 원인, 로그에 남는 중요 데이터는 암호화), 예외를 일으킬 수 있는 입력의 범위 검사, 서버에 설정한 기본 오류 페이지(`java.lang.Throwable`, 404, 500에 대한 `web.xml`의 `error-page`)나 리다이렉트 규칙, 메시지에 중요정보가 없는 오류 코드집을 확인합니다
- 보안약점 37번과 38번은 이 기준에 대응하지 않습니다(`D`: 요구사항 1번과 2번이 실질적으로 이를 포함하므로 함께 검토합니다)

## SR4: 세션통제

### SR4-1 세션통제

1. 세션 사이에 데이터를 공유하지 않습니다.
2. 세션을 안전하게 관리합니다.
3. 세션 ID를 안전하게 관리합니다.

- **점검 사항**
  - 스레드로 실행되는 클래스(서블릿, 컨트롤러, 싱글톤 서비스, JSP 선언부)에 읽고 쓸 수 있는 멤버 변수나 클래스 변수가 없습니다
  - 모든 페이지에서 로그아웃할 수 있고 세션을 완전히 제거합니다(`session.invalidate()`). 사용자의 연결이 끊어지면 세션을 제거합니다
  - 타임아웃: 중요 기능은 2분에서 5분, 위험이 낮은 애플리케이션은 15분에서 30분입니다. 유휴 세션은 서버가 제거합니다
  - 중복 로그인을 허용하지 않는다면, 이전 세션을 종료하거나 새 로그인을 거부합니다
  - 세션 ID는 서버가 안전한 난수 생성기로 128비트 이상으로 만들고, `HttpOnly` 쿠키로만 전송하며 URL 재작성으로는 절대 전송하지 않습니다
  - 로그인한 뒤에(세션 고정 공격에 대비), 장시간 연결에서는 주기적으로, 패스워드를 변경한 뒤에(재인증과 함께) 새 세션 ID를 발급합니다
- 제3장은 "(재)로그인할 때 세션 ID를 변경한다"라고 설명하고, 부록과 진단가이드는 "이전 세션 ID를 재사용하지 않는다"라고 설명합니다. 둘 다 같은 점검 사항을 뜻합니다
- **테스트 계획**: 여러 세션에서 공유 데이터를 변경, JavaScript로 세션 ID를 읽기, 로그인한 뒤와 시간이 지난 뒤의 세션 ID 갱신

## 산출물 예시

개발보안 가이드의 부록은 eGovFrame 공통 컴포넌트의 화면에 기준을 적용합니다. 화면 유형마다 어떤 기준이 필요한지 보여 주는 점검표로 사용합니다.

| 화면 | 적용하는 기준 |
|------|----------------|
| 데이터 입력(회원 가입) | SR1-1, SR1-5, SR1-6, SR1-10, SR2-3, SR2-7, SR2-8, SR3-1, SR4-1 |
| 데이터 조회(아이디나 패스워드 찾기) | SR1-1, SR1-5, SR2-3, SR2-4, SR2-7, SR2-8, SR3-1, SR4-1 |
| 데이터 수정과 삭제(게시물) | SR1-1, SR1-5, SR1-6, SR1-9, SR2-1, SR2-4, SR2-7, SR3-1, SR4-1 |
| 파일 업로드(첨부 파일이 있는 게시물) | SR1-1, SR1-5, SR1-6, SR1-9, SR1-10, SR2-1, SR2-4, SR2-7, SR3-1, SR4-1 |
| 파일 다운로드 | SR1-1, SR1-4, SR1-5, SR1-10, SR2-1, SR2-4, SR2-7, SR3-1, SR4-1 |
| 웹 에디터 | SR1-1, SR1-5, SR1-6, SR1-9, SR1-10, SR2-1, SR2-4, SR2-7, SR3-1, SR4-1 |
| 관리자 페이지 | SR1-1, SR1-5, SR2-1, SR2-4, SR2-7, SR3-1, SR4-1 |

SR1-1, SR1-5, SR2-7, SR3-1, SR4-1은 모든 화면에 나타납니다. 제3장의 로그인 유스케이스는 SR2-2(시도 횟수 제한)와 SR2-8(암호화된 채널)을 추가합니다.
