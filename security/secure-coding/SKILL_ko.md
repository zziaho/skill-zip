# 시큐어코딩 (소프트웨어 개발보안)

한국 정부의 소프트웨어 개발보안 제도에 따라 소프트웨어를 개발하고 검토할 때 참조하는 자료입니다. 행정안전부와 한국인터넷진흥원(KISA)이 발간한 가이드 두 종을 바탕으로 합니다.

| 가이드 | 판 | 사용 목적 |
|--------|----|-----------|
| 소프트웨어 개발보안 가이드 (전자정부 SW 개발·운영자를 위한 소프트웨어 개발보안 가이드) | 개정 5판, 2021.11. (파일 날짜 2021-12-29) | 정의, 대응 방안, 코드 예시, 설계 기준 |
| 소프트웨어 보안약점 진단가이드 | 개정 4판, 2021.11. | 진단 방법, 정탐과 오탐 코드 |

두 가이드는 모두 「행정기관 및 공공기관 정보시스템 구축·운영 지침」을 행정안전부고시 제2021-3호로 인용합니다. 현행본은 **행정안전부고시 제2025-1호**입니다(2025. 1. 2. 일부개정·시행, 2026-11-06에 law.go.kr에서 확인). 현행본의 소프트웨어 개발보안 조항은 가이드의 설명과 여전히 일치합니다. 제50조는 원칙과 의무 대상 사업, 적용 범위를, 제52조는 진단 기준을, 제53조는 감리 시 진단과 진단도구를, 제54조와 별표 4는 진단원을 정합니다. 별표 3(소프트웨어 보안약점 기준)에는 이 스킬이 다루는 설계 기준 20개와 보안약점 49개가 그대로 실려 있습니다. 고객에게는 현행 고시 번호를 인용하고, 이후 개정이 있었는지 law.go.kr에서 확인합니다.

두 가이드는 출처를 표시하도록 요구하며, 표시할 출처는 행정안전부·한국인터넷진흥원의 『전자정부 SW 개발·운영자를 위한 소프트웨어 개발보안 가이드』와 행정안전부·한국인터넷진흥원의 『소프트웨어 보안약점 진단가이드』입니다. 이 스킬은 가이드를 요약하고 재구성한 것이며, 가이드 원문을 옮기지 않았습니다.

## 사용 방법

1. 작업이 **설계**(요구사항, 아키텍처, 화면 설계 문서)인지 **구현**(소스 코드)인지 판단합니다.
2. 조회표에서 작업에 해당하는 항목을 찾고, 그 항목이 가리키는 파일**만** 읽습니다.
3. **개발**할 때는 작성하는 코드에 해당하는 모든 항목의 안전한 패턴을 따릅니다.
4. **검토**할 때는 각 항목의 **탐색** 줄로 후보를 찾고, **정탐** 줄과 **오탐** 줄로 후보마다 판단합니다. 정탐인 후보만 보고합니다.

## 제도의 적용 범위

| 항목 | 가이드의 규정 |
|------|---------------|
| 의무 대상 | 「전자정부법 시행령」 제71조제1항에 해당하는 사업입니다. 가이드는 이를 정보시스템 감리대상 사업으로 설명합니다. 그 밖의 사업도 적용할 수 있습니다(지침 제50조) |
| 신규 개발 | 설계 단계의 모든 산출물과 모든 소스 코드 |
| 유지보수 | 유지보수로 변경된 설계 산출물과 소스 코드 전체입니다(변경된 파일을 뜻하는지 변경된 행을 뜻하는지는 가이드에 나와 있지 않습니다) |
| 제외 대상 | 상용 소프트웨어 |
| 기준 | 설계단계 보안설계 기준 20개, 구현단계 보안약점 제거 기준 49개 |
| 진단 | 감리 법인이 별표 3의 보안약점이 제거되었는지 진단하고, 진단원을 우선 배치할 수 있습니다(지침 제53조). 진단도구를 사용한다면 국가보안기술연구소장이 인증했거나, 한국인터넷진흥원장이 확인했거나, 국가정보원장의 보안기능 확인서를 받은 도구여야 하며, 별표 3을 진단할 수 있어야 합니다. 진단가이드는 미탐을 줄이려고 수동 진단을 병행합니다. 1차 보고서에는 파일, 행, 보안약점 이름, 원인, 조치 방법을 적고, 2차 진단에서 제거 여부를 확인합니다 |

지침과 가이드는 모두 의무 대상의 사업 규모나 기관 목록을 제시하지 않고, 「전자정부법 시행령」 제71조제1항을 가리킵니다. 기준 금액을 임의로 말하지 않습니다.

## 표기 규칙

참조 파일의 모든 규칙에는 강도가 표시되어 있습니다.

| 강도 | 의미 | 검토할 때 보고하는 방식 |
|------|------|--------------------------|
| `R` | 보안약점이나 설계 기준 자체이며, 무엇이 취약한지에 대한 가이드의 판단입니다 | 결함(제거해야 할 보안약점) |
| `G` | 가이드가 제시하는 대응 방법입니다(라이브러리, 코드 패턴, 설정) | 권장 사항. 보안약점을 제거하는 다른 수정 방법도 똑같이 인정됩니다 |
| `D` | 가이드에 내용이 없거나, 일관되지 않거나, 오래되었거나, 틀린 부분에 대한 이 스킬의 판단입니다. 이유를 옆에 적어 둡니다 | 권장 사항. 가이드의 범위를 넘어선다는 점을 함께 알립니다 |

- **결함은 공식 번호와 한국어 이름으로 부릅니다.** 예를 들어 "보안약점 1 SQL 삽입"이나 "설계 기준 SR1-1 DBMS 조회 및 결과 검증"처럼 적습니다. 진단원과 감리원이 이 이름을 사용합니다.
- 가이드가 제시하는 정탐과 오탐 예시는 진단원과 의견이 갈릴 때 가장 강력한 근거입니다. "진단가이드 정탐 예" 또는 "진단가이드 오탐 예"로 인용합니다.
- 가이드의 코드에는 오기가 많습니다(예: `&&`가 들어갈 자리의 `||`, `strncpy` 대신 `stmcpy`). 이 스킬의 예시는 바로잡은 것입니다. 가이드의 코드를 읽어 보지 않고 그대로 복사하지 않습니다.
- 가이드의 예시는 Java(Spring, JSP, MyBatis, iBatis, Hibernate 포함), C, C#입니다. 이 스킬은 Java와 C만 유지합니다. 다른 언어는 코드가 아니라 정의와 판단 규칙을 적용합니다.

## 개발할 때

1. 외부 입력(요청 파라미터, 헤더, 쿠키, 파일, 환경 변수, 코드 밖에서 수정하는 프로퍼티, 소켓 데이터, 사용자가 작성한 DB 값)을 파악하고, 각 입력이 사용되는 위치를 확인합니다.
2. 입력이 도달하는 위치(쿼리, 명령어, 경로, 응답, 리다이렉트, 보안 결정)마다 해당 참조 파일을 읽고 안전한 패턴을 따릅니다.
3. 인증, 세션, 암호화, 중요 데이터를 다룰 때는 코드를 작성하기 전에 `references/security-features_ko.md`를 읽고, 직접 작성한 검사 대신 프레임워크의 보안 기능(예: Spring Security)을 사용합니다.
4. C 코드는 C 예시가 있는 항목도 함께 읽습니다. `references/input-validation_ko.md`의 보안약점 3번, 5번, 14번, 16번, 17번, `references/security-features_ko.md`의 20번, 28번, `references/time-error-code_ko.md`의 34번, 35번, 39번부터 42번, `references/encapsulation-api_ko.md`의 49번입니다.

## 검토할 때

1. **탐색** 줄로 후보를 나열합니다. 사용자가 진단도구 보고서를 가지고 있다면 그 보고서도 후보 목록으로 사용합니다.
2. 외부 입력에서 사용 지점까지 데이터 흐름을 따라가며 후보마다 **정탐** 줄과 **오탐** 줄로 판단합니다. 정탐만 보고합니다.
3. **오탐** 사례에 해당하는 도구 지적 사항은 오탐이라고 밝히고 해당 사례를 인용합니다.
4. 결함마다 파일과 행, 보안약점 번호와 한국어 이름, 강도, 원인, 수정 방법을 적습니다. `R` 결함을 먼저 묶어서 적고, 그다음에 `G`와 `D` 권장 사항을 적습니다.

## 범위 밖의 사항

보안약점 49개와 설계 기준 20개는 다음 사항을 다루지 않습니다. 이런 사항에는 보안약점 번호를 붙이지 말고, 범위 밖이라고 밝힙니다.

- 취약한 의존성과 SBOM. 개발보안 가이드는 Log4j와 SBOM을 기준 밖의 참고 자료인 부록(제5장 제6절 참고자료, "Top 10")에서만 언급하며, 개정 이력에는 추가된 시점이 기록되어 있지 않습니다.
- 클라우드, 컨테이너, 인프라 설정
- API 인증 방식(JWT, OAuth, OpenID Connect)의 설계. 코드에서 이를 사용하는 방식에는 보안약점 15번, 18번, 19번, 25번, 28번이 그대로 적용됩니다(검증하지 않은 토큰을 신뢰하는 문제, 누락된 검사, 약한 난수값, 생략된 인증서 유효성 검증).
- 어느 보안약점 정의에도 해당하지 않는 업무 로직 결함

객체 수준 인가(사용자가 요청한 레코드에 접근할 수 있는지 확인하는 검사, IDOR)는 **범위 안**에 있습니다. 진단가이드의 SR2-4 설계 예시는 데이터 수준의 접근 통제를 요구합니다. 삭제할 수 있는 권한이 있는 사용자라도 삭제하려는 레코드에 대한 권한을 검사해야 합니다. 이 검사가 누락되었다면 보안약점 19 부적절한 인가로 보고합니다(`D`: 가이드는 데이터 수준 검사에 보안약점 번호를 붙이지 않습니다. 19는 모든 실행 경로에서 접근 통제를 검사하지 않거나 불완전하게 검사하는 문제로 정의됩니다).

## 관련 스킬

`egovframe` 스킬을 설치했다면, 그 스킬의 PMD 규칙과 SQL 규칙이 여러 보안약점과 겹칩니다. 대응하는 규칙이 있는 항목은 **관련**에 그 규칙을 적어 두었습니다.
